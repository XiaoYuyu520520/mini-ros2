# The types the bridge's three registries know about.
#
# One line per entry: `<kind>\t<ros2 type name>`.
#
#   msg      a topic message      -> type_registry.cpp
#   srv      a service            -> service_registry.cpp
#   action   an action            -> action_registry.cpp
#
# This file is the single source of truth for *which* types the bridge
# understands. The table of C++ structs, the include list and the ordering
# are generated from it by `bridge/tests/generate_registries.py`, so adding a
# type is one line here plus the include the generator writes - not three
# hand-edited lists that can drift apart.
#
# What the generator does NOT generate: the pretty printer (`describe`) and
# the field setter (`applyFields`) of a type. Those carry decisions a
# generator cannot make - which fields are worth printing, how a sequence is
# summarised, what a friendly name for an enum value is - so they stay
# hand-written in the registry .cpp files, and a type without one falls back
# to the generic printer and to "no settable field".
#
# The order is the order of the table, and it is kept by hand so the
# generated file diffs cleanly: a new type goes at the end of its group.
#
# A type that is not listed here is not transcoded: the bridge passes it
# over with a warning, and `ros2 topic echo` prints a byte count.
